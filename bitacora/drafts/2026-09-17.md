The first version of a system always looks clean. It only has to lie to you once.

This week I extended something I'd built for one job so it could also handle a second, related one.

The first version had felt obviously right. Every shortcut in it looked like a design decision — because there was only one case it ever had to satisfy.

Then the second case showed up, close enough to the first that it was tempting to just bolt a parallel path onto what already worked. Ship it, move on.

I didn't. I went back and found the shape the first version should have had from the start — one path, not two, that both cases could sit inside.

It cost an extra day this week. It already saved me a rewrite I would have owed in a month.

The lesson I keep relearning as a forward-deployed engineer: you don't find out if an abstraction is right from the first use case. You find out from the first one you never designed for. Build for what is in front of you — but build it like you already know a second demand is coming, because it usually is.
